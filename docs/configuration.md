# Deployment configuration

The Rust runtime contains no deployment-specific account, repository or GitHub App identities. Supply them in the server repository's `policy.json`. See [policy.example.json](policy.example.json) for an organization deployment with a separate human maintainer and a `trunk` default branch. Example IDs are placeholders; obtain the actual immutable GitHub IDs before deploying.

The `deployment` section declares the server and integration repository names, immutable IDs and default branches; the repository-owning account; the human maintainer login; Client and Server App IDs and bot logins; the approval reviewer ID/login; the required check producers; and release/runtime-update branch names. Top-level `owner_id`, `client_bot_id` and `server_bot_id` bind the corresponding identities. `trusted_committers`, repository capabilities, release strategies and sensitive paths are also deployment policy. A Terraform provider release is selected by the repository's release strategy, rather than its name.

The integration repository must differ from production. Both repository names must belong to the configured owning account. Principal IDs must be nonzero and distinct, and the policy check must be produced by the configured Server App. Malformed settings fail before operations proceed; there are no personal defaults.

A stable runtime archive contains its executable and policy together, covered by the same attestation. The installation action copies both files to the executable directory. The runtime reads `policy.json` beside its executable, never from the caller's working directory. `SECUREFIX_POLICY_PATH` is available for a trusted local controller to select an explicit configuration; do not populate it from caller inputs or PR content. Configuration is immutable within a process. Production also loads the policy from the current server default-branch commit and requires its deployment identities to match the trusted runtime before writes.

GitHub workflow YAML is deployment configuration too: configure the App secret names, token permissions, protected environment, trigger guards and attestation repository/signer to match this policy. Private keys and tokens remain GitHub secrets and are never placed in policy. The reusable workflow implementations use the verified runtime; installing another user's policy or changing a workflow guard does not grant authority over their repositories.

Candidate integration transports the policy with the candidate artifact and mounts it read-only beside the executable inside the isolated container. Trusted host validators use their own verified runtime policy. The candidate receives only installation tokens whose repository list consists of the configured integration repository; it does not receive production keys or the server read token.

Cargo-launched development processes default to the fixed test fixture policy through `.cargo/config.toml`. This keeps tests independent of the real deployment policy and exercises separate human/repository-owner IDs. Override `SECUREFIX_POLICY_PATH` explicitly when using `cargo run` for your deployment. This Cargo configuration does not affect installed release executables.
