# Repository settings and merge-control activation

`repo-settings.yml` is an orchestration workflow. The trusted Rust CLI validates policy and performs all GitHub API changes. Desired repository state is stored in `repo-settings/repository.json`, `repo-settings/collaborator.json`, and `repo-settings/rulesets/`; the repository capability set and tag-protection flag are in `policy.json`.

Scheduled runs reconcile only repositories with the `settings` capability and reconcile controlled-merge rulesets only when they already exist and are active. Schedules never create or reactivate a controlled-merge ruleset. A manually selected repository can be reconciled or created when `create_if_missing` is enabled; creating a repository is limited to manual dispatch. Removing `protect_tags` from policy intentionally leaves an existing `all-tags` protection in place. Retiring that protection requires an explicit reviewed deletion.

Repositories with the `release` capability have immutable releases enabled during settings reconciliation. The CLI reads the repository's current immutable-release state, enables it only when needed, then verifies the result. Removing the release capability does not disable immutable releases. This uses GitHub's [repository immutable releases REST endpoints](https://docs.github.com/en/rest/repos/repos#enable-immutable-releases), which require repository administration write permission.

Controlled-merge activation is a separate full-list operation. Before activation, dispatch `repo-settings.yml` with an empty repository input and set `merge_controls_ready` only after verifying the operational prerequisites and running an end-to-end merge test. The Rust preflight independently checks all merge-capable repositories, current default-head status checks from the expected GitHub Apps, required ruleset settings, current server-pinned client wrappers, `civitaspo-bot` write access, and that the Server App token is scoped to exactly the complete configured set. It also requires the main environment's `CIVITASPO_BOT_PR_APPROVE_TOKEN` and verifies that it authenticates as `civitaspo-bot` with write access to each repository. It checks clients first and applies the server ruleset last. The job also requires the GitHub App token action to issue the requested permissions; token creation failure stops the rollout.

The readiness input is an operator attestation, not a substitute for those API checks. It cannot prove that a real merge and release staging flow has been exercised. Follow the rollout runbook and perform those tests before enabling merge controls. For an emergency stop, disable the controlled-merge ruleset directly in GitHub; schedules only update rulesets that are already active and will not reactivate a disabled ruleset.

Every privileged CLI command verifies that its source revision is exactly the current `securefix-server` main revision. CLI binaries are built by the dedicated main-push producer and distributed through immutable SemVer GitHub Releases whose tags resolve to the exact promoted source SHA. The reusable loader verifies the archive's source and signer before passing it to privileged jobs as an immutable same-run artifact ID. A newly merged server revision deliberately invalidates older caller binaries; wait for runtime publication and retry from the newest workflow revision.
