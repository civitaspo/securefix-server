# Repository settings and merge-control activation

`repo-settings.yml` is an orchestration workflow. The trusted Rust CLI validates policy and performs all GitHub API changes. Desired repository state is stored in `repo-settings/repository.json`, `repo-settings/collaborator.json`, and `repo-settings/rulesets/`; the repository capability set and tag-protection flag are in `policy.json`.

Scheduled runs reconcile only repositories with the `settings` capability and reconcile controlled-merge rulesets only when they already exist and are active. Schedules never create or reactivate a controlled-merge ruleset. A manually selected repository can be reconciled or created when `create_if_missing` is enabled; creating a repository is limited to manual dispatch. Removing `protect_tags` from policy intentionally leaves an existing `all-tags` protection in place. Retiring that protection requires an explicit reviewed deletion.

Repositories with the `release` capability have immutable releases enabled during settings reconciliation. The CLI reads the repository's current immutable-release state, enables it only when needed, then verifies the result. Removing the release capability does not disable immutable releases. For the initial control bootstrap, the owner must enable immutable releases for `civitaspo/securefix-server` through the repository administrator UI or API before the first code PR merges; the deployed v0.2.20 runtime cannot perform this prerequisite. This uses GitHub's [repository immutable releases REST endpoints](https://docs.github.com/en/rest/repos/repos#enable-immutable-releases), which require repository administration write permission.

Before the first control-bootstrap code PR merges, an owner must also remove Renovate bypass from all nine live controlled-merge rulesets, retain the sole Server App `pull_request` bypass, disable native auto-merge, and verify that no requests remain queued. This permanent live-settings rollout requires explicit owner approval and must use the repository administrator UI or API while the deployed v0.2.20 runtime is still available; do not create a temporary ruleset exception. No production settings change is made by this proposal.

Default-branch protection is split between integrity, review/check, and controlled-merge rules. The integrity ruleset retains required signatures, linear history, pull-request-only updates, and deletion and non-fast-forward protection. The review/check ruleset requires the configured review and status checks. Both controlled-merge rulesets name only the configured Server App with `pull_request` bypass mode; live settings preflight rejects any other actor or mode. That bypass does not replace Rust owner, review, check, exact-head, or control-identity validation, and mutations still run through the serialized server Actions lane. Runtime distribution opens reviewable caller PRs. Native Renovate auto-merge is disabled, so a Renovate PR also needs an explicit owner `/merge` command after the required checks pass.

Controlled-merge activation is a separate full-list operation. Before activation, dispatch `repo-settings.yml` with an empty repository input and set `merge_controls_ready` only after verifying the operational prerequisites and running an end-to-end merge test. The Rust preflight independently checks all merge-capable repositories, current default-head status checks from the expected GitHub Apps, required ruleset settings, current server-pinned client wrappers, `civitaspo-bot` write access, and that the Server App token is scoped to exactly the complete configured set. It also requires the main environment's `CIVITASPO_BOT_PR_APPROVE_TOKEN` and verifies that it authenticates as `civitaspo-bot` with write access to each repository. It checks clients first and applies the server ruleset last. The job also requires the GitHub App token action to issue the requested permissions; token creation failure stops the rollout.

The readiness input is an operator attestation, not a substitute for those API checks. It cannot prove that a real merge and release staging flow has been exercised. Follow the rollout runbook and perform those tests before enabling merge controls. For an emergency stop, disable the controlled-merge ruleset directly in GitHub; schedules only update rulesets that are already active and will not reactivate a disabled ruleset.

Every privileged command verifies the active control identity. The active descriptor selects the source-bound attested runtime and policy snapshot; an ordinary main update does not activate a new runtime. Publication and caller distribution are separately dispatched after review and activation. See [migration and rollout](migration.md) and [ADR 0009](adr/0009-active-control-revision.md) for the proposed lifecycle and bootstrap constraint.
